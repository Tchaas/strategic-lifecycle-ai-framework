**Earlier code review:** 2026-09-15, commit `28a75f2`, compared with `Target_Architecture_v3.4.pdf`.

## 0. Decisions that govern the work

| Decision | What implementation must do |
|---|---|
| No customers use the database, and there is no real data to preserve. | Recreate the test database as needed. Do not plan a customer-data transfer or preserve the old structure for compatibility. |
| Extend the existing application. | Keep working code and existing controls where they fit the agreed behavior. No rebuild from scratch is requested. |
| Accounts and permissions come first. | Complete sign-up, sign-in, email confirmation, password recovery, workspace membership, and roles before business-page work. |
| Build in the order a person uses the application. | Complete each page together with its server operations and saved information. Part B defines the order and completion checks. |
| Use the real application connection from the beginning. | No sample-data fallback, pretend save, or later project to connect completed screens. Empty workspaces show empty results. |
| Keep the current appearance and structure. | Extend the current layout, navigation pattern, forms, tables, and controls with the required pages. A different mockup does not authorize a different theme. |
| Appearance changes require explicit approval. | Present suggestions separately. Do not change colors, fonts, spacing, branding, layout structure, or visual treatment without the owner's approval. |
| Avoid temporary shortcuts that require rebuilding later. | Establish account and permission rules before other pages depend on them. Remove replaced behavior in the same piece of work and test the full user action. |
| No fixed deadline. | Remove the old three-day deadline and the previous schedule estimates. Estimate a step only after its screens, rules, and checks are defined. |
| Stripe is out of scope. | Do not build billing, purchases, Stripe settings, or Stripe-specific fields. |
| AI credit charging is deferred. | Keep it separate from the current work. Existing protection against excessive requests still matters. |
| Real email is required, using SES. | Confirmation, password recovery, invitations, and account-link confirmation must deliver real messages. |
| Limits on objectives, streams, activities, and cases are removed. | Remove both server limits and matching counters or disabled controls when completing the affected work. Workspace member limits are a separate rule. |

### 0.1 Which source to follow

1. The owner's latest explicit instructions take priority.
2. This document's current decisions and build order govern v3.4 work.
3. The v3.4 requirements supply detailed behavior where they do not conflict with those decisions.
4. The running UI supplies the existing appearance and structure. Additional UI supplied by the
   owner informs new pages and their sequence; it does not automatically replace the theme.
5. Earlier HTML references, implementation notes, and deviation entries explain previous work.
   They do not override the decisions above.

If sources disagree about a behavior that has not been settled, record the exact disagreement
and resolve it before implementing that behavior. Do not invent a rule. Continue independent
work whose requirements are already clear.

The original PDF and the exact additional UI used for the earlier comparison are not identified
as checked-in files in this document. Before relying on a detail found only in either source,
record its accessible location and version in B.3. A quotation in an older analysis is not a
substitute for inspecting the source.

### 0.2 Database setup

There is no customer-data migration to plan. The local and hosted databases contain disposable
development data. The existing database creation scripts can be replaced with a clean initial
setup as the agreed v3.4 structure is implemented.

During the database work, check the intended database connection, create the agreed structure
from empty, and verify it against the application. Repeat for each development environment in
use. Old revision numbers are setup details, not a reason to delay accounts and permissions.
This planning update does not execute or authorize a database reset.

Technical note: the repository uses Alembic to create the tables. Its directory is named
`migrations`; using that existing tool does not imply transferring or preserving old records.
`backend/migrations/env.py` reads `DATABASE_URL` from the shell environment.

### 0.3 What is already available

Sign-up, sign-in, server permission checks, and many page connections already exist. They need
to be checked and extended, not assumed absent. However, some connected pages still mix saved
information with sample information. A page connection count is not proof that the page is
complete. Check each field, selection list, total, action, and destination.

**`users`** — `app/models/users.py`
Missing `is_platform_admin boolean NN default false` (IT11) and `deactivated_at timestamptz` (IT19).

### A.5 Behavioural gaps in tables that already exist

These are the ones most likely to be missed, because nothing in the schema looks wrong.

1. **Workspace creation does not create the business architecture.**
   `provision_workspace_for_user` (`app/services/workspace_service.py:56`) inserts a workspace
   and a member, then returns. S01/S02 require the architecture in the *same transaction*, so
   that "a workspace without an architecture cannot exist."

2. **Signup provisions a workspace.** `AuthService.signup`
   (`app/services/auth_service.py:69-91`) calls `provision_workspace_for_user`. IT02 requires
   signup to create a **workspace-less** account. This was a deliberate earlier decision —
   Deviation #5 in `DEVIATIONS.md` — that v3.4 reverses. `workspace_name` appears **41 times**
   across the backend, tests and frontend.

3. **`GET /workspaces` returns a list.** `WorkspaceService.list_workspaces` selects all
   memberships. IT01 says it returns zero or one.

4. **Four structural caps are enforced that v3.4 abolishes.** Rule S04 is explicit:
   *"There is no limit on the number of strategic objectives, value streams, key activities,
   capabilities, supporting components, or business cases a workspace may create."*
   Currently enforced as `409 cardinality_limit`:

   | Constant | Value | File |
   |---|---|---|
   | `OBJECTIVE_LIMIT` | 3 | `app/services/strategy_service.py:38` |
   | `VALUE_STREAM_LIMIT` | 6 | `app/services/value_stream_service.py:20` |
   | `KEY_ACTIVITY_LIMIT` | 6 | `app/services/key_activity_service.py:17` |
   | `CASE_LIMIT` | 10 | `app/services/business_case_service.py:34` |

   The frontend mirrors them in `src/rules/lifecycleRules.ts:14-22` (`cardinalityLimits`), used
   by `checkCardinality` and at `lifecycleRules.ts:136`.

5. **S08 is not enforced.** `value_streams.linked_department_id` and
   `business_capabilities.owning_department_id` exist and are nullable, but nothing requires an
   owning department before a component is promoted to `active`.

6. **`created_by_user_id` is NOT NULL with CASCADE** (`app/models/mixins.py`, `AuditMixin`).
   The v3.4 baseline states user references are nullable with `ON DELETE SET NULL` "so removing
   a user never destroys a cost ledger, an audit row, or authored history." This is a direct
   reversal of Deviation #11's rule ("NOT NULL FKs are ownership → CASCADE") as applied to the
   audit column. Deleting a user today would cascade-delete everything they authored.

## Part B — Implementation plan

### B.0 Build order: follow the user

The earlier dashboard-first order and theme replacement are withdrawn. There is no separate
"connect the frontend later" step. The numbered **steps** below are the build order.
The numbered **groups** in B.4 retain the earlier technical inventory for reference only;
their numbers are not an instruction to build one group at a time.

#### Step 1: Define the pages and account rules

Write down the path for a new account, an invited person, and a returning user. Identify the
current page to extend or the new page to add, what the person enters, what each button does,
what is saved, and which page follows. Use the owner's supplied UI for details not established
by the existing screens.

Create a permission table for each action: signed out, signed in without a workspace, workspace
member, workspace administrator, and application operator. An application operator is separate
from a company administrator. Specify who can view, create, edit, delete, invite, and change roles.
Use v3.4's detailed rules; unresolved permissions remain explicitly undecided.

**Complete when:** the account and workspace page records in B.1 are filled in, the applicable
source locations are recorded, and there are no guessed rules in the work about to begin.
Later business-page details can be settled before their own step.

#### Step 2: Prepare account storage and shared permission checks

Extend the existing account code and prepare a clean database setup for the agreed account,
workspace, membership, invitation, and account-status rules. Replace `is_admin` with explicit
`admin` / `member` roles, enforce at most one workspace per user, and distinguish application
operators from workspace administrators. Define how disabled accounts and retired workspaces
lose access before later pages rely on these checks.

Use the same server checks for every page. Keep workspace records private from outsiders.
Update the existing account tests as part of this work; do not add a second temporary account
system. Final table counts are a consequence of the agreed requirements, not a target to guess.

**Complete when:** setup works from an empty database and automated checks prove the account,
membership, and permission rules. This supporting step is not a claim that a user page is done.

#### Step 3: Complete account pages with real email

Complete sign-up, confirmation pending, email confirmation, sign-in, sign-out, forgotten password,
password reset, and the agreed Google sign-in/linking behavior. Ordinary sign-up creates an
account without a workspace. A confirmed user without a workspace goes to setup; a returning
member goes to their workspace. Preserve an invitation destination through sign-in.

Send real emails through SES. Handle repeated submissions, delivery failure, expired or used
links, resending confirmation, an incorrect password, and reopening the browser. Establish
account-setting and account-closing rules now; connect their screens when their required
workspace behavior is available in Step 4. Do not grant application access simply because the
browser says someone is signed in.

**Complete when:** a person can register, receive and follow the email, sign in, refresh, sign
out, and recover access through the actual pages. Test failed requests as well as success.
Shared account protections must work before moving to business pages.

#### Step 4: Complete workspace setup, invitations, members, and account settings

A confirmed account can create a workspace or follow the appropriate invitation path.
Workspace creation saves the workspace, its creator's administrator membership, and its required
starting business-architecture record together. If one part fails, none of those parts is saved.
The business-architecture record is the company's shared record of how its work is organized.

Complete invitation preview, registration through an invitation, acceptance by an existing
account, role assignment, cancellation, and member management. The invited account must match
the intended recipient. Apply the v3.4 invitation verification rule and prevent a second
workspace membership. Protect the last administrator.

Connect account settings, sign-in methods, and account closure to the agreed rules for members,
administrators, and retired workspaces. Resolve any unclear effect on other members before
building a destructive action.

**Complete when:** two people can create and join the same workspace using actual emails and
screens; allowed actions succeed and forbidden actions fail on the server. A third account in
another workspace cannot read or change their records. Account closure and loss of access are
tested. Accounts, roles, and membership are complete before Step 5.

#### Step 5: Complete company information, departments, and the dashboard

Connect company details and department forms to saved workspace records, including the required
department contacts and ownership links. A new workspace shows empty lists and truthful totals.
The dashboard appears where the agreed journey puts it, but all visible totals come from the
database. No sample companies, member lists, or financial figures appear as the user's work.

**Complete when:** edits survive refreshing and signing in again; available department choices
match saved departments; dashboard values match saved records. Add summaries that need later
business pages as those pages are completed, without pretending unfinished summaries work.

#### Step 6: Complete the business pages in the agreed page order

Record and follow the owner's actual sequence for objectives, company work and capabilities,
business cases, discovery, features, requirements, deliverables, and implementation results.
This is a list of required areas, not a guessed new navigation design. Complete any record a
page depends on before expecting the user to select it.

For each page, complete its reads, writes, permissions, required fields, links, status changes,
totals, and errors together. Remove obsolete limits in both the server and the page. Include
the required AI actions with that page: request, review, edit, save, discard, and recover an
unfinished suggestion. Do not defer all AI connections to a later blanket exercise.

**Complete when:** the page passes B.2 and works with information entered through earlier
pages. Walk the journey from sign-up again after each completed step.

#### Step 7: Complete downloads, feedback, and application support pages

Build actual downloads with their waiting, success, expiry, and failure states; save feedback;
and complete operator pages and workspace-controlled support access. Their access rules come
from Step 1. Granting support access must be explicit and time-limited, and relevant operator
actions must be recorded. Do not expose unfinished or pretend controls in completed pages.

**Complete when:** requested files download and contain the correct saved records, feedback is
stored, and support access is denied or expires as specified. Verify the full journey through
all completed pages with separate accounts.

#### What is not scheduled

Stripe and theme replacement are out of scope. AI credit charging remains deferred. There is
no final step to attach pages to the server and no blanket approval to remove or reorganize
existing pages. The previous day/week estimates are withdrawn; new estimates require defined
page work, confirmed external-service needs, and observed progress.

### B.2 When a page is complete

- [ ] Every visible record, selection, and total comes from the correct saved workspace data.
- [ ] The action reaches the server, checks permission and input, saves, and displays the result.
- [ ] Refreshing and signing out/back in show the same saved result.
- [ ] Invalid or failed saves do not appear successful or silently show sample data.
- [ ] Signed-out users, unauthorized members, and other workspaces cannot bypass access checks.
- [ ] Relevant loading, empty, error, expired-link, and repeat-submission cases are handled.
- [ ] Related records and totals update correctly; earlier completed steps still work.
- [ ] Replaced sample-data paths and obsolete rules are removed from the completed page.
- [ ] Required emails, AI requests, and downloads have been exercised through the actual service.
- [ ] Existing style and structure are preserved; approved exceptions have a recorded approval.
- [ ] Focused server checks, the frontend build, and the relevant browser checks pass.
- [ ] The page record lists changed files, results, and any unresolved issue; unresolved required work means it is not complete.

Automated tests may create temporary records or simulate failures. This does not authorize
sample-data fallback in the application. Demonstrations use records created through its real
forms. Until an older page is completed, record its limitations; do not count it as working.
